# CLAUDE.md — 歴史教師の探究ノート 開発指針

このファイルはプロジェクトの「開発上の憲法」である。
実装・デザイン・コンテンツ設計のすべての判断はここに立ち返って行う。

---

## サイトの基本思想

このサイトは、高校教員（日本史・歴史総合・公共）が授業実践・読書・思考を記録する**個人の探究ノート**である。

生徒向け教材サイトではない。生徒の個人情報（氏名・作品・写真等）は一切含めない。

### 中心は「概念タグ」である

授業単元でも、読書ノートでも、大きな問いでもない。**概念タグ**がサイト全体の結節点である。

- 概念タグを起点に、授業単元・読書ノートを横断的に行き来できる
- 一つの概念が複数の授業・複数の本でどう現れるかを見渡せる
- 教師自身が知識を再構成するための「知識ネットワーク」を作ることが目的

新しい機能・ページを設計するとき、「これは概念タグを中心とした構造を強化するか？」を必ず問う。

## コンテンツの種類と位置づけ

### 授業単元（`/units/`）

実際の授業実践の記録。授業で話したこと・使った資料・設計した問いをアーカイブする。

- **大きな問い**は授業設計の軸として重要だが、サイト全体の中心ではない
- 授業には「大きな問いに直接回収されない知識・資料・話題」も含まれる。それでよい
- サイト全体の横断接続は概念タグが担う。大きな問いはあくまで「その授業の構造」を示すもの

**フロントマターの原則**
- `concepts:` は必須。これがない単元はネットワークの孤島になる
- `bigQuestion:` は授業設計の軸として記録するが、UIの最上位に置きすぎない
- `overview:` は3行以内。長くしない
- `answer:` はページ末尾に置く。授業を通じた結論であり、知識の終着点ではない

### 読書ノート（`/books/`）

本の要約ではなく、**引用データベース**である。

引用を読んだ人が自分で考えられる余白を残すことが目的。AI の解釈を前面に出さない。

**サイト公開の原則**

公開サイト（`src/content/books/*.md`）には **publish スクリプトが AI 選択した引用のみ** を入れる。掲載引用数は著作権上の観点から必要最小限にとどめる。

```
## テーマ見出し

> 原文引用（長くてよい。原文のまま）

*著者名『書名』（年）*
```

これ以外は原則として書かない。

**書いてはいけないもの**
- AI要約・AI解説・引用後のコメント
- 「授業への使い方」「授業での活用法」
- 引用の意味を説明するまとめ文（引用の余白を潰す）

**Vault 構造（`books-vault/`）**

`books-vault/` は全引用の蓄積庫（マスターデータ）。`.gitignore` に入れ、GitHub にも Vercel にも送らない。

3層構造で管理する：

| 層 | ファイル | 役割 | 誰が作るか |
|---|---|---|---|
| Vault | `books-vault/[slug].md` | 全引用の蓄積 | gas_vault.js（AI が自動生成） |
| 公開用 | `src/content/books/[slug].md` | 公開引用のみ | publish スクリプト（AI が選択） |
| 修正 | — | 必要なときだけ手動修正 | 教師（最後の仕上げのみ） |

- 教師は Vault を日常的に確認・選別しない
- `<!-- featured -->` は通常運用では使わない（将来の手動指定に備えて設計上の余地だけ残す）
- Vault は NotebookLM への入力元としても使う

**gas_vault.js の役割**

ページ画像（Google Drive）を入力とし、◎・縦線・横線を画像から認識して Vault Markdown を自動生成する。

- 入力：Drive `books-vault/[slug]/` のページ画像 + 既存 OCR（`_MERGED` Doc）
- 出力：`books-vault/[slug].md`（全引用・テーマ見出し・`<!-- concepts: ... -->`）
- AI 要約・解説・授業活用メモは生成しない
- `<!-- featured -->` は生成しない
- 教師は通常この出力を確認しない

**generate.py（publish スクリプト）の役割**

公開したい本が決まったときだけ手動実行する。

- 入力：`books-vault/[slug].md`（全引用）
- 出力：`src/content/books/[slug].md`（公開引用のみ）
- AI が以下の基準で引用を自律的に選択する：
  - 概念理解に役立つ（知識ではなく思考の材料になる）
  - 授業との接続性が高い
  - 著者の視点・論点がよく表れている
  - 引用だけで考える余白がある（解説なしで読める）
- 生成後に教師が必要なら最後だけ修正する

### 思考ノート（`/notes/`）— 例外的コンテンツ

**常設の主要コンテンツにしない。**

基本構造は「授業単元・読書ノート・概念タグ」の三本柱で成立させる。

思考ノートを作るのは、以下の条件がそろったときだけ：
- 複数の本を読み
- 授業でも繰り返し扱い
- それでもまだ考え続けたいテーマ

「とりあえず書く」コンテンツにしない。数が少なくてよい。

## 概念タグの設計原則

### 概念タグこそ育てる対象

概念タグページ（`/concepts/[concept]/`）は、将来的にこのサイトの最重要ページになる。

- 授業単元、読書ノート、（将来）思考ノートが一覧できる「知識ハブ」
- 概念の説明・関連概念へのリンクも追加できる構造を目指す

### 概念タグの粒度

- 抽象度が近いタグは統一する（例：「帝国主義」と「近代帝国主義」は一本化）
- タグは各コンテンツの自己申告だが、乱立を防ぐため既存タグを優先して使う
- 新しい概念タグを追加するときは、既存タグ一覧（`/concepts/`）を必ず確認する

### 将来の中核的概念への対応

文部科学省が正式な「中核的概念」を公表した場合でも、既存の概念タグ・URL を変更せずに対応できる設計を維持する。

- 現時点では `parents` / `scope` / `subjectRole` / `officialKey` などの階層フィールドを UI で使わない
- スキーマには `.optional()` として予約はできるが、ページには表示しない
- 概念ページの URL（`/concepts/[概念名]/`）は将来にわたって変更しない
- 概念間の階層は現時点では固定しない。公式定義が示されてから追記・拡張する

## UI・デザイン原則

### 基本姿勢

- **情報量を増やしすぎない**——セクションを追加したくなったら、まず削れるものを探す
- **余白を大切にする**——詰め込まない。読む速度に合わせた余白
- **引用を主役にする**——blockquote は装飾ではなく、ページの主役
- **AIの解説を前面に出さない**——生成テキストであっても、それとわからないほど整える。わからないなら削る
- **機能追加より余白を優先する**——できることが増えても、教師や読者が考えるための空白は削らない

### blockquote のスタイル

引用は論文引用スタイル（明朝体・アンバー左ボーダー・薄い背景）を維持する。
これを崩すリファクタリングは行わない。

### テーマ

現在のテーマは **Parchment**（羊皮紙）。`src/styles/global.css` で管理。
テーマ切り替えUI（ThemeSwitcher）は存在するが、Parchmentを基準に設計する。

## 技術原則

### フレームワーク

- **Astro 5** 静的出力（`output: 'static'`）
- React・Vue などのフロントエンドフレームワークは導入しない
- インタラクションは最小限のバニラ JS（フィルタリング・トグルのみ）

### コンテンツ管理

- すべてのコンテンツは `src/content/` 以下の Markdown + YAML フロントマター
- スキーマは `src/content.config.ts` で Zod により型定義する
- コンテンツ追加は Markdown ファイルを置くだけで完結させる

### ファイル構造の原則

```
src/content/units/      ← 授業単元 Markdown
src/content/books/      ← 読書ノート公開用（publish 時に AI が選択した引用のみ）
src/pages/              ← ルーティング（Astro ページ）
src/components/         ← 再利用コンポーネント
src/styles/global.css   ← 唯一のグローバル CSS

books-vault/            ← 読書ノート全引用保管（.gitignore 必須）
                           GitHub にも Vercel にも送らない
                           教師は通常確認しない。publish で公開用を生成する
```

- コンポーネントは「複数ページで使う」ものだけ作る
- ページ固有のスタイルはそのページの `<style>` に書く

### 命名規則

- コンテンツファイル：`kebab-case.md`（例：`teikoku-shugi.md`）
- コンポーネント：PascalCase（例：`ConceptBadge.astro`）
- CSS クラス：kebab-case（例：`.book-card`）

### 公開・デプロイ

- **プラットフォーム**：Vercel（Hobby プラン）
- **リポジトリ**：個人 GitHub アカウントの **private** リポジトリ
- **GitHub Pages は使わない**：`src/content/books/*.md` などのソース Markdown が公開リポジトリに露出するため
- Vercel は GitHub private リポジトリから自動デプロイする。公開されるのはビルド済みの HTML/CSS/JS のみ
- `books-vault/` は `.gitignore` に追加し、GitHub にも Vercel にも送らない

## 「やらないこと」リスト

以下は、一見よさそうに見えても、このプロジェクトの設計思想に反する。

| やりたくなること | やらない理由 |
|---|---|
| AI生成の長い解説を読書ノートに追加する | 引用の余白を潰す。AIの解釈を押しつけることになる |
| 「授業への使い方」セクションを読書ノートに設ける | 読書ノートを教材化する。本来の位置づけから外れる |
| 思考ノートを積極的に増やす | 例外的コンテンツが常設化すると構造が崩れる |
| 授業単元を「学習サイト」風にする | このサイトは教師の記録であって、生徒向けコンテンツではない |
| 概念タグなしのコンテンツを追加する | ネットワークの孤島を作る |
| セクションや情報を増やす方向でデザインを変える | 余白と引用を主役にする原則に反する |
| React 等を導入する | Astro の静的シンプル構成を壊す |
| GitHub Pages で公開する | `src/content/books/*.md` のソースが公開リポジトリに露出する。原文引用を扱うため HTML のみを公開する方針に反する |
| リポジトリを public にする | ソース Markdown が GitHub 上で公開される。private リポジトリ + Vercel の構成を維持する |

## 開発フローの原則

1. **実装前に方向性を確認する**——コード変更を始める前に、設計思想に合っているか言語化する
2. **一度に複数の変更を混ぜない**——構造変更・デザイン変更・コンテンツ変更は分けて行う
3. **ビルドで確認する**——変更後は必ず `npx astro build` でエラーがないことを確認する
4. **変更後は git commit する**——作業単位でコミットし、ロールバックできる状態を保つ

## 付録：コンテンツ追加チェックリスト

### 授業単元を追加するとき

- [ ] `concepts:` に既存タグを優先して設定した
- [ ] `bigQuestion:` は授業設計の軸であり、知識の全体を代表するものとして書いていない
- [ ] `overview:` は3行以内
- [ ] 本文は授業で実際に話したこと・使ったことの記録になっている
- [ ] 関連する読書ノートがあれば `relatedBooks:` に追加した

### 読書ノートを追加するとき

**Vault 生成（gas_vault.js を GAS で実行）**
- [ ] Drive の `books-vault/[slug]/` にページ画像と `meta.json` を配置した
- [ ] GAS で `processBook()` を実行した
- [ ] 必要なら引用を原本と照合し修正した（通常は不要）

**サイト公開（generate.py をローカルで実行）**
- [ ] `python generate.py [slug]` を実行した
- [ ] 公開用 `src/content/books/[slug].md` が生成された
- [ ] 必要なら最後だけ手動修正した
- [ ] `concepts:` に既存タグが設定されているか確認した（3〜5個を目安）
- [ ] 関連する授業単元があれば `relatedUnits:` に追加した
- [ ] `summary:` は任意。書く場合は2〜3行以内

### 新しいコンポーネントを追加するとき

- [ ] 複数ページで使うもの、または既存の HTML が著しく複雑になる場合のみ作る
- [ ] インタラクションが必要なら最小限のバニラ JS で書く
