# 読書ノート公開レビュー

`python generate.py <slug>` が選定した公開用引用（`src/content/books/[slug].md`）を、教師の手を煩わせずレビューし、コミット可能な状態に仕上げる。

## この手順が存在する理由

`gas_vault.js` の自動publish経路（②）は、Geminiが引用を選んでそのままGitHubにcommitするだけで、**機械的チェックも他ファイルとの照合も一切行わない**。このスキルを「教師の代わりにClaudeが判断する」ためだけに使い、以下のStep 1・4・5を省略すると、②と実質同じ（AIが選んで即確定）に戻ってしまう。

**絶対原則：Step 1・4・5は、たとえ全自動で実行する場合でも省略しない。** この3つが②にはできない「二重チェック」の中身そのものであり、ここを飛ばすなら、このスキルを使う意味自体がなくなる。

## 実行手順

### Step 0: 対象を特定する

`<slug>` が渡されていなければ尋ねる。`rekishi-hp/src/content/books/[slug].md` が存在するか確認する。無ければ「まだ `generate.py <slug>` が実行されていません」と伝えて中断する。

### Step 1: 機械チェックを実行する（省略不可）

`generate.py` 実行直後の出力に警告が出ていればそれを使う。出ていない・見当たらない場合は以下で単体実行する。

```bash
cd rekishi-hp/books-vault && python -c "
from audit_citations import split_frontmatter, check_citations_text
from pathlib import Path
content = Path('../src/content/books/<slug>.md').read_text(encoding='utf-8')
body = split_frontmatter(content)
for r in check_citations_text(body):
    print(r['heading'], ':', r['issues'])
"
```

加えて、ファイル末尾が `*著者名『書名』（年）*` の形で正しく閉じているか目視確認する（閉じていなければ Gemini 生成がトークン切れで途中終了した証拠。Step 2 の除外では直せないので Step 3 へ）。

### Step 2: 警告への対応を判断する

警告が出た引用ブロックを1件ずつ実際に読み、機械的に処理せず内容で判断する。

- **too_short / truncated**（30字未満・文末が不自然）→ 原則除外する。除外すると総ブロック数が15を大きく下回る場合は、除外せず理由つきで教師に報告する
- **stray_marker / stray_symbol**（`> >` の二重表記・`◎` の混入）→ 記号だけを取り除いて残す。引用文の言葉そのものは変えない
- 除外する場合は該当ブロック（見出し・引用・出典・`<!-- concepts: -->`・区切りの `---`）をまるごと削除する

### Step 3: 生成そのものの異常をチェックする

Step 1 でファイル末尾が途中終端だと分かった場合、これは選定ミスではなく生成の失敗なので、ブロックの除外や修正では対処しない。**このスキルの範囲では再生成しない**（無限ループ・無駄なAPI呼び出しを避けるため）。教師に「`<slug>` はトークン切れで生成が途中終了しています。`python generate.py <slug>` の再実行が必要です」と報告し、以降のStepは中断する。

### Step 4: relatedUnits を横断判断する（省略不可）

`rekishi-hp/src/content/units/*.md` を全て読み、この本の引用内容（タグの一致ではなく実際の本文の主題）と各単元の本文（`bigQuestion` / `overview` / 本文）との内容的な親和性を評価する。

- 判断基準は `rekishi-hp/CLAUDE.md` の設計思想と同じ：無理な紐付けはしない。合う単元がなければ何も追加しない
- 追加する場合は必ず両方向を更新する：本の `relatedUnits` と、単元側の `relatedBooks`。片方だけの更新はしない

### Step 5: relatedBookLinks を横断判断する（省略不可）

他の `src/content/books/*.md` の内容（`summary` と引用）と比較し、明確な主題的関連がある場合のみ `relatedBookLinks` に追加する（`slug` + `note`）。

- 無理な紐付けはしない。1対1で明確に説明できる関連だけを対象にする
- 追加する場合は原則双方向（AのrelatedBookLinksにB、BのrelatedBookLinksにA）。`note` は各方向で内容を書き分けてよい（例：時代背景側→接続先を説明する書き方、接続先→時代背景側を参照する書き方）
- このフィールドはサイトのUIには表示されない（Obsidian Vault側の「## 関連書籍」に変換されるのみ）。表示目的の情報ではなく、あくまで書籍間の関連の記録であることを踏まえて書く

### Step 6: concepts・summary を確認する

- `concepts` は `generate.py` の時点でマスター語彙にフィルタ済みだが、念のため `src/data/concepts/*.json` に存在するか再確認する
- `summary` が2〜3文程度で本の主題を捉えているか目視確認する。明らかにおかしい場合のみ修正する（基本的にはそのまま採用してよい）

### Step 7: 書影を確認する

`src/assets/covers/[slug].jpg`（または `.png` / `.webp`）の有無を確認する。無ければ「書影が未設置です」と報告するだけにする（画像ファイルなので生成・取得はできない）。

### Step 8: ビルド確認

```bash
cd rekishi-hp && npx astro build
```

エラーが出た場合は原因を説明し、該当箇所を修正する。

### Step 9: レビュー結果を報告し、コミットの可否を確認する

以下の形式で報告してから、コミット・pushしてよいか教師に確認する。**確認なしにcommit・pushしない。**

```
## 読書ノート公開レビュー完了：<書名>

- 機械チェック: <検出件数>件（除外<N>件・記号除去<N>件・問題なし<N>件）
- 生成異常: なし / あり（Step 3 で中断）
- relatedUnits: <追加なし / 追加した単元名と理由>
- relatedBookLinks: <追加なし / 追加した本のタイトルと理由>
- 書影: 設置済み / 未設置
- astro build: 成功 / エラー（内容）
```

承認が得られたら、変更したファイルだけを対象にコミットする（無関係なファイルは含めない）。

```bash
git add src/content/books/<slug>.md
# relatedUnitsを追加した場合は対象の units/*.md も
# relatedBookLinksを追加した場合は対象の他の books/*.md も
git commit -m "読書ノート: <書名>の公開レビュー完了"
git push
```
